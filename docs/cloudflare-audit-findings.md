## Key Observations

1. **`fs` + `path` + `process.cwd()` pattern is pervasive**: Nearly all data-loading modules read JSON from disk at runtime using `readFileSync(join(process.cwd(), ...))`. This is the #1 incompatibility — Workers have no filesystem.

2. **`crypto` is partially compatible**: Cloudflare Workers support `crypto.subtle` (Web Crypto API) natively. `createHash`, `createHmac`, `randomBytes`, and `timingSafeEqual` require the Node.js compatibility flag (`nodejs_compat`) or migration to Web Crypto equivalents.

3. **`pg` driver requires socket replacement**: Workers don't support raw TCP. Options: Neon serverless driver, Supabase HTTP client, or Cloudflare Hyperdrive (proxies TCP over HTTP).

4. **`@xenova/transformers` is already gated**: The opt-in mechanism (`ENABLE_LOCAL_EMBEDDINGS`) means this won't accidentally run on Workers, but it must be documented as an absolute no-go.

5. **`Buffer` is available with `nodejs_compat`**: Workers with the `nodejs_compat` flag support `Buffer`, so this is lower priority.

6. **All data loading is build-time-safe**: The `readFileSync` calls read pre-built JSON files. They could be converted to `import` statements or pre-bundled at build time for Workers compatibility.

## 9. Edge Runtime Proof-of-Concept (Task 7.4)

### What was tested

Added `export const runtime = "edge"` to `src/app/about/page.tsx` — a static marketing page with no Node.js-only dependencies.

### Result

✅ **Build passes** (`npm run build` and `npx tsc --noEmit` both succeed).

### Observations

1. **Static generation disabled**: Next.js emits a warning: "Using edge runtime on a page currently disables static generation for that page." The `/about` page changes from `○ (Static)` to `ƒ (Dynamic)`.

2. **Why this page works**: It only imports:
   - `MarketingPageFrame` (React component using `next/link` and `StudyNav` which is `"use client"`)
   - String constants from `@/lib/marketing` (no Node.js APIs)

3. **Why `/api/feedback` doesn't work for edge**: The feedback route imports `rate-limit.ts` which uses `createHash` from Node.js `crypto`. The `pg` driver in `db.ts` also uses TCP sockets. Both are incompatible with Cloudflare Workers without `nodejs_compat` flag.

4. **No other API routes are edge-compatible**: All existing API routes depend on `rate-limit.ts` (crypto), `db.ts` (pg), `answer-sources.ts` (fs/path), or Supabase server (requires `cookies()` headers).

### Recommendation

- For the Cloudflare migration, static marketing pages (`/about`, `/terms`) are the easiest to move to edge runtime.
- API routes will require either the `nodejs_compat` flag or migration to Web Crypto + serverless Postgres drivers.
- The static generation tradeoff means edge runtime should only be applied to pages that benefit from edge rendering (personalized content, geo-routing) — not pages that are identical for all users.
